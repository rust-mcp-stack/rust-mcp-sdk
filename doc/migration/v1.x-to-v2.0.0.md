# v1.x to v2.0.0 Migration Guide

v2.0.0 migrates `rust-mcp-sdk` from MCP **2025-11-25** to **2026-07-28**
(stateless protocol). This guide covers the breaking changes and their
replacements.

## Overview

The 2026-07-28 protocol removes the `initialize` handshake, the task
system, `ping`, `setLevel`, `subscribe`/`unsubscribe`, and server→client
RPCs. Everything becomes per-request via `_meta`. A new mid-request
turn-around (MRTR) mechanism replaces server→client input requests.

## Batching removed

The `send_batch` method has been removed from all traits (`McpDispatch`, `McpClient`, `McpServer`) and their implementations. Batch message variants are gone. Group all requests into separate calls — there is no replacement.

## Sessions and resumability removed

MCP 2026-07-28 is stateless. The following are gone with no replacement:

- `Mcp-Session-Id` HTTP header
- `/mcp` GET and DELETE endpoints (only POST is supported)
- `Last-Event-ID` for SSE resumability
- `InMemoryEventStore` and `InMemorySessionStore`
- `event_store` field from `AxumServerOptions` and `ActixServerOptions`
- `session_store` field from `AxumServerOptions` and `ActixServerOptions`
- `AxumServerOptions::default()` no longer auto-starts with an event store
- `make_resumable` and `store_event` methods
- `McpAppState` no longer carries session/event stores
- Client no longer tracks `session_id`, no `terminate_session`, no standalone GET stream for notifications
- `McpHttpError` no longer has `SessionIdMissing`/`SessionIdInvalid` variants
- SSE `cors_middleware` no longer exposes `MCP-Session-Id` header via `Access-Control-Expose-Headers`
- `parse_session_id_header()` removed
- `ID_SEPARATOR` removed
- `handle_http_get()`, `handle_http_delete()` removed

## Standalone server→client requests removed

The 2.0 protocol does not have separate RPCs for servers to request input from clients. The following methods are gone with no replacement (use MRTR instead):

- `McpServer::request_elicitation()` — removed
- `McpServer::request_root_list()` — removed
- `McpServer::create_message()` / `request_message_creation()` — removed

The replacement is MRTR: return `ServerResult::InputRequiredResult` from tool/prompt/resource handlers, and use `client.call_tool()` which auto-retries.

## Mechanical renames

| 1.x (2025-11-25) | 2.0 (2026-07-28) |
|---|---|
| `InitializeResult` | [`ServerDetails`] |
| `InitializeRequestParams` | [`ClientDetails`] |
| `ResultFromServer` | [`ServerResult`] |
| `ElicitFormSchema` | `ElicitRequestFormParamsRequestedSchema` |
| `ClientRoots` | `Option<serde_json::Map<String, Value>>` |

## Envelope restructuring

The JSON-RPC envelope enums no longer have one variant per
request/notification. Standard requests and notifications are grouped under a
`Standard` wrapper, with `Custom` reserved for unknown methods:

- `ClientJsonrpcRequest`: flat variants → `Standard(ClientRequest)` | `Custom(JsonrpcRequest)`
- `ServerJsonrpcNotification`: flat variants → `Standard(ServerNotification)` | `Custom(JsonrpcNotification)`
- `ClientJsonrpcNotification`: dropped `InitializedNotification`, `ProgressNotification`,
  `TaskStatusNotification`, `RootsListChangedNotification`; remains
  `CancelledNotification` | `CustomNotification`
- `ServerJsonrpcRequest`: dropped `PingRequest`, `GetTaskRequest`,
  `GetTaskPayloadRequest`, `CancelTaskRequest`, `ListTasksRequest`

## Removed types & fields

- `PingRequest`, `SetLevelRequestParams`, `SubscribeRequestParams`, `UnsubscribeRequestParams`
- `ElicitCompleteParams`, `TaskStatusNotificationParams`
- `ClientTaskResult`, `CreateTaskResult`, `GetTaskParams`, `GetTaskResult`, `GetTaskPayloadParams`, `CancelTaskParams`, `CancelTaskResult`
- `McpMetaEx` trait
- `Tool.execution` field (no task system)
- `CallToolRequestParams.task` field (no task system)
- `ElicitResult.meta` field
- `CallToolRequestParams.meta` changed from `Option<RequestMetaObject>` to required `RequestMetaObject`
- `Icon.theme` still exists, but the `From<&str>` impl was removed — use the `mcp_icon!` macro

## Macro changes

### `#[mcp_tool]`

The `execution` attribute is no longer supported.

### `mcp_icon!`

The `theme` value is now resolved via string match (`"dark"` / `"light"`)
instead of `From<&str>`. Unrecognized themes default to `None` instead of
`IconTheme::Light`.

## Handler signature changes

### Server handlers

Every `ServerHandler` method now receives `context: &RequestContext` as
the third parameter (before `runtime`):

```rust
// 1.x
fn handle_call_tool_request(
    &self,
    params: CallToolRequestParams,
    runtime: Arc<dyn McpServer>,
) -> Result<CallToolResult, CallToolError>;

// 2.0
fn handle_call_tool_request(
    &self,
    params: CallToolRequestParams,
    context: &RequestContext,   // <-- NEW
    runtime: Arc<dyn McpServer>,
) -> Result<ServerResult, CallToolError>;  // <-- ServerResult
```

### Return type changes

Three handler methods now return [`ServerResult`] instead of their
specific result types:

| Method | 1.x return | 2.0 return |
|---|---|---|
| `handle_call_tool_request` | `CallToolResult` | `ServerResult` |
| `handle_read_resource_request` | `ReadResourceResult` | `ServerResult` |
| `handle_get_prompt_request` | `GetPromptResult` | `ServerResult` |

Wrap existing returns with `.map(|r| r.into())` or return
`ServerResult::InputRequiredResult(...)` directly for MRTR.

```rust
// 1.x
t.call_tool(&runtime).await

// 2.0
t.call_tool(&runtime).await.map(|r| r.into())
```

## Per-request metadata

Every request carries `_meta` (a [`RequestMetaObject`]) with the
client's protocol version, capabilities, and identity. The server
receives this via [`RequestContext`]:

```rust
struct RequestContext {
    pub protocol_version: ProtocolVersion,
    pub client_capabilities: ClientCapabilities,
    pub client_info: Option<Implementation>,
    pub progress_token: Option<ProgressToken>,
    pub log_level: Option<LoggingLevel>,
}
```

On the client side, [`McpClient::request`] automatically stamps
`_meta` on every outgoing request using [`ClientDetails`].
You no longer need to construct `InitializeRequestParams`.

```rust
// 1.x
let init_params = InitializeRequestParams { ... };
let client = client_runtime::with_transport_options(init_params, ...);

// 2.0
let details = ClientDetails {
    client_info: Implementation { name: "my-client".into(), version: "1.0".into(), ... },
    capabilities: ClientCapabilities::default(),
};
let client = client_runtime::with_transport_options(details, transport_opts, handler, None);
```

## Server identity

Servers advertise their identity via `server/discover` instead of
`initialize`. Create a [`ServerDetails`] and populate the runtime:

```rust
// 1.x
let server_details = InitializeResult {
    server_info: Implementation { ... },
    capabilities: ServerCapabilities { ... },
    protocol_version: ProtocolVersion::V2025_11_25.into(),
    ...
};

// 2.0
let server_details = ServerDetails {
    server_info: Implementation { ... },
    capabilities: ServerCapabilities { ... },
    instructions: Some("Helpful text"),
    meta: None,
    // No protocol_version — declared per-request via _meta
};
```

The SDK automatically stamps `io.modelcontextprotocol/serverInfo` on
every response's `_meta`.

## Caching fields on all results

All list and read results now carry caching directives:

```rust
// Every ListToolsResult, ListResourcesResult, ReadResourceResult, etc.
// 1.x
ListToolsResult { tools: ..., meta: None, next_cursor: None }

// 2.0
ListToolsResult {
    tools: ...,
    cache_scope: ListToolsResultCacheScope::Private,
    result_type: "complete".to_string(),
    ttl_ms: 0,
    meta: None,
    next_cursor: None,
}
```

## MRTR (Mid-Request Turn-Around)

When the server needs input from the client, instead of a separate
`input/request` RPC it returns `InputRequiredResult` and the client
retries the **same request** with the answers in `inputResponses`.

### Server handler

```rust
fn handle_call_tool_request(
    &self, params: CallToolRequestParams,
    context: &RequestContext, runtime: Arc<dyn McpServer>,
) -> Result<ServerResult, CallToolError> {
    // If input is needed
    return Ok(ServerResult::InputRequiredResult(InputRequiredResult {
        input_requests: Some(InputRequests(BTreeMap::from([...]))),
        request_state: None,
    }));
}
```

### Client auto-driver (recommended)

Use the MRTR-aware `ClientRuntime` methods that retry automatically
(up to 10 rounds):

```rust
let result = client.call_tool(params).await?;   // auto-retries
let result = client.get_prompt(params).await?;  // auto-retries
let result = client.read_resource(params).await?;  // auto-retries
```

### Client manual (`_once` variants)

```rust
let result = client.request_tool_call_once(params).await?;
match result {
    ServerResult::CallToolResult(r) => { /* success */ }
    ServerResult::InputRequiredResult(ir) => {
        let responses = process_input_requests(ir.input_requests.unwrap());
        // retry with .with_input_responses(...)
    }
    _ => { /* error */ }
}
```

### RequestState security

The `requestState` blob is **untrusted** (sent by the client verbatim).
Use [`RequestStateCodec`] to HMAC-sign it if you need integrity:

```rust
let codec = RequestStateCodec::from_base64_key(env!("MCP_STATE_KEY"))?
    .with_max_age(Duration::from_secs(60));

// Encode
let state = codec.encode_str(&serde_json::to_string(&my_state)?);

// Decode and verify
let decoded = codec.decode_str(&state)?; // None if tampered/expired
```

## Subscriptions

The `subscriptions/listen` RPC replaces `subscribe`/`unsubscribe`.

```rust
let resp = client.request_subscriptions_listen(
    SubscriptionsListenRequestParams {
        notifications: SubscriptionFilter {
            tools_list_changed: Some(true),
            prompts_list_changed: Some(true),
            resource_subscriptions: vec!["file:///project/".into()],
            resources_list_changed: Some(true),
        },
        meta: RequestMetaObject::default(),
    },
).await?;
```

The `-32021` capability check now validates per-request:

```rust
impl ServerHandler for MyHandler {
    fn required_capabilities_for_method(&self, method: &str) -> Vec<RequiredClientCapability> {
        if method == "tools/call" {
            vec![RequiredClientCapability::Sampling]
        } else {
            vec![]
        }
    }
}
```

## Error code changes

| Error | Code | Used for |
|---|---|---|
| `HEADER_MISMATCH` | -32020 | HTTP `MCP-Protocol-Version` header ≠ `_meta` version |
| `MISSING_REQUIRED_CLIENT_CAPABILITY` | -32021 | Client didn't declare a required capability |
| `UNSUPPORTED_PROTOCOL_VERSION` | -32022 | Unknown/unsupported protocol version |

## Transport & web framework crates

`AxumRuntime` and `ActixRuntime` proxy methods are now provided by the
[`McpHttpServer`] trait as default implementations. If you import
`McpHttpServer` you can call `send_notification` and all `notify_*`
methods (`notify_log_message`, `notify_tool_list_changed`,
`notify_resource_list_changed`, `notify_prompt_list_changed`,
`notify_resource_updated`, `notify_cancellation`, `notify_progress`,
`notify_custom`) on any runtime without duplicating them yourself.

```rust
use rust_mcp_sdk::McpHttpServer;

let runtime: AxumRuntime = ...;
runtime.notify_tool_list_changed(&session_id, None).await?;
```

> Standalone server→client *requests* (`request_elicitation`,
> `request_root_list`) were removed from 2.0 — use MRTR
> (`ServerResult::InputRequiredResult`) instead.

## Example migration

The quick-start server has been updated:

- `InitializeResult` → [`ServerDetails`]
- Handler added `context: &RequestContext` parameter
- Return types changed to `Result<ServerResult, _>`
- `ListToolsResult` includes `cache_scope`/`result_type`/`ttl_ms`
- `McpServerOptions` no longer has `task_store`/`client_task_store`
